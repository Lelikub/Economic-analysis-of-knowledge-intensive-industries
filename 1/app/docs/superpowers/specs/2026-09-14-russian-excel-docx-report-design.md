# Русификация Excel и итоговый Word-отчёт — проектное решение

## Цель

Сделать все видимые пользователю элементы расчётной книги Excel русскоязычными и добавить итоговый Word-отчёт с параметрами, таблицами, графиками и выводами, построенными только на результатах действующего расчётного конвейера.

## Границы изменения

- Расчётная логика Python, определения метрик и независимость Excel Ground Truth не меняются.
- Существующий Markdown-отчёт сохраняется; Word-отчёт создаётся как дополнительный обязательный результат.
- Все команды расчёта, тестирования и генерации запускаются интерпретатором `.venv/Scripts/python.exe` из рабочей папки `1/app`.
- Microsoft Word для генерации DOCX не требуется. Microsoft Excel используется только для реального пересчёта формул XLSX, как и раньше.

## Русский интерфейс Excel

Листы получают имена: `Исходные данные`, `Метрики`, `Затраты`, `TTM`, `Стресс-тест`, `Журнал сверки`, `Структура OPEX`, `Допущения`, `Проблемы данных`.

На русском языке выводятся:

- заголовки столбцов;
- отображаемые названия параметров и метрик;
- сценарии, статусы, причины расхождений и интерпретации;
- единицы измерения в человекочитаемом виде;
- математические записи, перечни параметров и пояснения формул;
- допущения, проблемы данных и подписи диаграмм.

Для трассируемости рядом с русским названием исходного параметра сохраняется его техническое имя из CSV. Внутренние ключи Python и CSV не переименовываются.

Формульные ячейки остаются настоящими формулами XLSX. Функции внутри формул (`IF`, `OR`, `EXP`, `NA`, `ABS`) записываются в стандартном международном формате, который требуется файлу XLSX независимо от языка интерфейса Excel. Русским становится соседнее человекочитаемое пояснение формулы.

Видимые статусы книги локализуются следующим образом:

- `PASS` → `СОВПАДАЕТ`;
- `FAIL` → `РАСХОЖДЕНИЕ`;
- `NOT_COMPUTABLE` → `НЕ РАССЧИТЫВАЕТСЯ`;
- baseline → `Базовый`;
- stress → `Стрессовый`.

Внутренние статусы Python и значения экспортных CSV остаются стабильными, чтобы не ломать программные интерфейсы и аудит предыдущих расчётов.

## Word-отчёт

Новый обязательный файл: `output/Итоговый_отчет.docx`.

Он создаётся библиотекой `python-docx` из уже сформированного `ReportContext`. WordBuilder не пересчитывает метрики и не содержит вручную заданных итоговых чисел.

Структура документа:

1. титульный блок и цель работы;
2. использованные исходные файлы;
3. таблица входных параметров базового и стрессового сценариев;
4. формулы, единицы измерения и пояснения;
5. таблица рассчитанных производственных и экономических метрик;
6. состояние реального пересчёта Excel и таблица сверки Excel/Python;
7. таблица стресс-сравнения;
8. параметры и результаты TTM;
9. диаграмма структуры OPEX;
10. график сравнения FPY, OEE и TEEP для базового и стрессового сценариев;
11. допущения и проблемы качества данных;
12. автоматически сформированные выводы по рассчитанным метрикам.

Числа форматируются по смыслу: доли как проценты, денежные значения как доллары США, физические показатели с их единицами. Отсутствующая массовая ресурсоёмкость выводится как `НЕ РАССЧИТЫВАЕТСЯ` с причиной, а не заменяется нулём.

## Визуализация

Существующая диаграмма OPEX сохраняется и получает корректные русские подписи. Добавляется `output/сравнение_эффективности.png` — сгруппированная столбчатая диаграмма FPY, OEE и TEEP в процентах для базового и стрессового сценариев. Оба изображения включаются в DOCX.

## Поток данных

`CSV → ProductionData → validation → MetricsResult/TTM/StressComparisonRow → ReportContext → Markdown + DOCX`

Независимая ветка Excel остаётся:

`CSV → формулы XLSX → реальный пересчёт Excel → cached values → MetricsHarness`

После сверки её результаты также входят в общий `ReportContext`.

## Изменения компонентов

- `excel.py`: русские отображаемые словари, имена листов, ссылки формул и запись русских значений журнала сверки.
- `visualization.py`: исправленные русские подписи OPEX и новый построитель графика эффективности.
- `word_reporting.py`: изолированный построитель DOCX из `ReportContext` и готовых PNG.
- `pipeline.py`: создание второго графика и DOCX, добавление обоих файлов в обязательные результаты и журнал событий.
- `requirements.txt`: зависимость `python-docx`.
- `README.md` и `1/data/ARCH.md`: запуск, выходные файлы и архитектура отчётности.

## Обработка ошибок

- Невозможность создать DOCX или обязательный график завершает pipeline ошибкой, потому что это обязательные результаты.
- Недоступность COM Excel обрабатывается существующим способом и явно отражается в отчётах.
- Отсутствующее вычислимое значение выводится с русским статусом, но не подменяется фиктивным числом.
- Все пути изображений проверяются перед вставкой в Word.

## Критерии приёмки

- В книге присутствуют девять листов с утверждёнными русскими именами.
- Все заголовки, человекочитаемые значения, пояснения формул, статусы и комментарии книги русифицированы; допустимы только общеупотребимые аббревиатуры и отдельные технические имена CSV в специальном столбце.
- Формулы книги остаются формульными ячейками, пересчитываются Excel и дают прежние числовые результаты.
- DOCX существует, непуст, содержит все обязательные разделы, не менее шести таблиц и два встроенных изображения.
- В DOCX присутствуют фактические FPY, OEE, TEEP, CPU и TTM из `ReportContext`, включая корректный статус отсутствующей массовой ресурсоёмкости.
- Pipeline возвращает XLSX, два CSV, Markdown, DOCX и два PNG как обязательные выходные файлы.
- Автоматические тесты и итоговый запуск выполняются из `1/app` через `.venv/Scripts/python.exe`.
