# Архитектура решения практического занятия № 1

## 1. Назначение

Проект реализует воспроизводимый вычислительный pipeline для анализа пилотного производства EUV-фоторезиста. Один запуск читает исходные CSV, валидирует данные, рассчитывает показатели в Python, создаёт независимую Excel-модель с формулами, пересчитывает её установленным Microsoft Excel, сравнивает два вычислительных слоя, выполняет стресс-тесты и формирует отчётные артефакты.

Архитектурный принцип: исходные данные имеют один источник, но расчёты Python и Excel реализованы независимо. Числа, рассчитанные Python, не записываются в Excel как эталонные результаты.

## 2. Границы проекта

- Рабочий каталог приложения: `1/app`.
- Входные данные: CSV из `1/data`.
- Исходные требования и методология: PDF и Markdown из `1/task`.
- Итоговые расчётные артефакты: `1/app/output`.
- Журнал выполнения: `1/app/logs/execution.log`.
- Этот архитектурный документ: `1/data/ARCH.md`.
- Бизнес-логика находится в Python-модулях; notebook не является обязательным и не используется как единственный вычислительный слой.

## 3. Поток данных

```text

  │                                         │                         │
```

Каждый крупный этап создаёт запись в системном журнале. `MetricsHarness` формирует отдельный табличный журнал сравнения значений.

## 5. Компоненты

### 5.1 Модель данных

`ProductionData` — типизированный `dataclass` со всеми параметрами производственного сценария. После загрузки расчётный код не обращается к значениям через строки или `DataFrame`.

`ParameterMetadata` хранит исходное имя, единицу, описание и источник параметра. `MetricsResult` хранит рассчитанные значения и статусы вычислимости. Для отсутствующей физической величины используется явный статус `NOT_COMPUTABLE`, а не `0`, бесконечность или выдуманное число.

### 5.2 Загрузка и валидация

`CsvProductionLoader` проверяет обязательные столбцы, уникальность параметров, пропуски, числовые типы и единицы, затем создаёт `ProductionData`. `DataValidator` отделяет обычные ошибки входа от намеренных стресс-условий.

Проверяются временные диапазоны, объёмы выпуска, выход годных, срок амортизации, параметры TTM, отрицательная энергия и специальные ограничения сценария. Ошибки возвращаются как структурированные записи, пригодные для отчёта и логирования.

### 5.3 Расчёты Python

`OperationalMetricsCalculator` является единым фасадом расчёта и формирует типизированный `MetricsResult`. Внутри него отдельно рассчитываются операционные показатели, затраты и доступные виды ресурсоёмкости; хранение данных, Excel, логирование и визуализация в класс не входят.

Формулы:

- `FPY = First_Pass_Good_Units / Actual_Output`;
- `Final Yield = Final_Good_Units / Actual_Output`;
- `Availability = Actual_Hours / Planned_Hours`;
- `Normative Cycle Time = Planned_Hours / Target_Output`;
- `Performance = Normative Cycle Time × Actual_Output / Actual_Hours`;
- `Quality = FPY`;
- `OEE = Availability × Performance × Quality`;
- `Utilization = Planned_Hours / Calendar_Hours`;
- `TEEP = OEE × Utilization`;
- `Energy Cost = Energy_kWh × Energy_Cost_Rate`;
- `Monthly Depreciation = Equipment_CAPEX / Amortization_Years_Economic / 12`;
- `Total Manufacturing Cost = Raw Material Cost + Energy Cost + OPEX Overhead + Monthly Depreciation`;
- `Energy Intensity = Energy_kWh / Final_Good_Units`;
- `Economic Intensity = Total Manufacturing Cost / Final_Good_Units`;
- `CPU = Total Manufacturing Cost / Final_Good_Units`.

Экономическая ресурсоёмкость и CPU совпадают численно для данного набора данных, потому что обе определены как полная производственная стоимость на литр итоговой годной продукции. В отчёте они остаются отдельными понятиями.

Массовая ресурсоёмкость не вычисляется: CSV не содержит массы потреблённого сырья. Требуемое дополнительное поле — например, `Raw_Material_Mass_kg`. Стоимость сырья на литр допускается только как явно обозначенный стоимостной proxy.

### 5.4 TTM

`TTMCalculator` реализует:

```text
L = 1 - (1 / (1 + r)^Δt) × exp(-αΔt) × ((T - Δt) / T) × I(Δt)
```

Для `Δt = 0` и открытого окна результат равен нулю. При `Δt >= T` сохранённая стоимость принимается равной нулю, штраф — единице. При закрытом рыночном окне штраф равен единице. `T <= 0`, `r <= -1`, отрицательная задержка и индикатор вне `{0, 1}` являются ошибками входа.

Рассчитываются два раздельных сценария:

- сценарий задания: `r = 0.10`, `α = 0.15`, `T = 3`;
- сценарий CSV: `r = 0.12`, `α = 0.18`, `T = 3`.

### 5.5 Excel Ground Truth

`ExcelGroundTruthBuilder` создаёт книгу со вкладками `Source Data`, `Metrics`, `Costs`, `TTM`, `Harness Log`, `Stress Test`, `OPEX`, `Assumptions` и `Data Issues`. Во все расчётные ячейки записываются Excel-формулы со ссылками на исходные значения.

Книга сохраняется, затем пересчитывается через установленный Microsoft Excel посредством COM automation. COM-сеанс изолирован в короткоживущем процессе `excel_worker.py`, запущенном тем же Python-интерпретатором: это гарантирует завершение жизненного цикла Excel до чтения книги и исключает RPC fault при освобождении COM-прокси. После сохранения пересчитанной книги значения читаются в режиме `data_only=True`. В журнале фиксируются события `EXCEL_FORMULA_WRITTEN`, `EXCEL_RECALC_STARTED`, `EXCEL_RECALC_COMPLETED` и `EXCEL_VALUE_READ`.

Если Excel automation недоступна, pipeline сохраняет книгу с формулами, помечает Ground Truth как не пересчитанный, не создаёт фиктивные результаты harness и даёт инструкцию по ручному пересчёту.

### 5.6 Harness

`MetricsHarness` сравнивает результаты Excel и Python с централизованным абсолютным допуском `1e-9`. Для каждой метрики сохраняются Excel Value, Python Value, абсолютное и относительное отклонения, допуск, статус, вероятная причина и timestamp.

### 5.7 Стресс-сценарий и визуализация

Стресс-сценарий загружается из отдельного CSV; comparison CSV программно проверяет изменения тарифа `0.22 → 0.66`, FPY `75% → 40%` и задержки `0 → 0.5`. Сравнение baseline/stress включает FPY, OEE, TEEP, Energy Cost, Economic Intensity, CPU и TTM penalty.

`OpexVisualizer` проверяет сумму долей `25 + 20 + 30 + 15 + 10 = 100%`, строит столбчатую диаграмму и вставляет PNG в Excel.

### 5.8 Отчётность и логи

`ReportBuilder` создаёт `output/report.md` только из программно полученных результатов. Отчёт включает mapping параметров, размерности, результаты, интерпретацию, допущения, Data Quality Report, Data Gaps, stress comparison, TTM-сценарии и итоговый checklist.

Системный logger пишет одновременно в консоль и файл в формате `timestamp | level | module | stage | message`. Основные события не выводятся через `print`.

## 6. Ошибки и специальные значения

- Нулевой знаменатель приводит к типизированному статусу `MetricStatus.NOT_COMPUTABLE`; значение сохраняется как `None`, а не как бесконечность.
- Полный брак даёт `FPY = 0`, `OEE = 0`; CPU и интенсивности при `Final_Good_Units = 0` получают `NOT_COMPUTABLE`.
- Отрицательная стоимость сырья запрещена в обычном baseline, но разрешается как `INTENTIONAL_STRESS_CONDITION` в тесте субсидирования.
- NaN, пропуски и несогласованные единицы являются ошибками входа.
- Необработанные исключения логируются с контекстом этапа и приводят к ненулевому коду завершения.

## 7. Тестирование

Разработка ведётся test-first. Модульные тесты покрывают:

- формулы FPY, Final Yield, OEE, TEEP, затрат и TTM;
- полный брак, идеальный завод и субсидирование сырья;
- нулевые знаменатели, отсутствующий параметр и NaN;
- нарушения временных и объёмных диапазонов;
- отрицательное энергопотребление;
- неверный индикатор рыночного окна;
- `Δt = 0`, `Δt = T`, `Δt > T`;
- проверку comparison CSV;
- наличие Excel-формул и независимость Excel от Python-результатов;
- корректность harness и списка обязательных выходных файлов;
- сумму долей OPEX, равную 100%.

Интеграционный тест запускает pipeline на исходных CSV. Финальная проверка включает полный `pytest`, запуск `python main.py`, повторную проверку артефактов и просмотр журнала на ошибки.

## 8. Допущения и обнаруженные проблемы данных

1. `Calendar_Hours = 720` соответствует месяцу из 30 дней, поэтому амортизация считается за месяц.
2. Нормативное время цикла выводится как `Planned_Hours / Target_Output`; отдельного поля в CSV нет. Размерность: `h/L`.
3. Для интенсивностей и CPU знаменателем служит `Final_Good_Units`, так как это итоговый объём продукции, прошедшей контроль качества.
4. В pilot CSV `Delay_Years = 0.5`, но comparison CSV задаёт baseline `Delay_Years = 0`. Для стресс-сравнения источником baseline/stress является comparison CSV; pilot CSV рассматривается как самостоятельный производственный сценарий.
5. Параметры TTM задания и CSV противоречат друг другу и поэтому рассчитываются раздельно.
6. Масса сырья отсутствует; массовая ресурсоёмкость физически не вычислима.
7. Поле `Actual_Output` трактуется как объём, запущенный/обработанный в производстве, в соответствии с описанием CSV и формулами задания.

## 9. Критерии завершения

Работа считается завершённой, когда:

- все CSV прочитаны и проверены;
- Python-метрики рассчитаны без ручной подстановки итогов;
- Excel содержит формулы и реально пересчитан Microsoft Excel либо ограничение явно зафиксировано;
- harness не содержит необъяснённых расхождений;
- все автоматические тесты пройдены;
- stress comparison, OPEX PNG, execution log, workbook, harness CSV и итоговый Markdown-отчёт созданы;
- `README.md` содержит единую команду запуска;
- `ARCH.md` отражает фактическую, а не только планируемую архитектуру.
